# Crawler Feature — Full-Stack Analysis
*Generated 2026-07-19*

## 1. How it works, end to end

**Backend** (`backend/crawler/`): `discover_websites_task` (Celery, scheduled every `CRAWLER_DISCOVERY_INTERVAL_SECONDS`, default 12h) runs Bing/Serper searches for each enabled `CrawlSource`'s discovery query, filters hits (`discovery_qualify.py`), and saves qualifying domains as `DiscoveredDomain` rows, then enqueues `crawl_domain_task` for each. That task does a robots.txt-respecting, rate-limited BFS crawl (`crawler.py`) of the domain, then enqueues `analyze_domain_task`, which scores the crawled content (`scoring.py`, spaCy/rule-based/Gemini) and — above `CRAWLER_MIN_SCORE_THRESHOLD` (default 40) — enqueues `score_and_create_prospect_task`, which promotes the domain into `leads.Prospect` via `prospect_pipeline.py`. Progress is tracked on a `CrawlRun` (one per discovery cycle) and per-domain on `CrawlRunDomainResult`. A separate `event_processor.py` path derives `EventProspect` rows for East-Africa event/procurement qualification.

**Frontend** (`frontend/src/features/crawler/` + `features/admin/crawler/`): `CrawlerHomePage` is a stats/workflow dashboard; `CrawlerDiscoverPage` is an ad-hoc "search now" workflow (preview → queue → crawl); `CrawlerDomainsPage`/`CrawlerRunsPage`/`CrawlerRunDetailPage` browse discovered domains and run history. Admin has parallel, mostly read-only pages over `CrawlSource`/`CrawlRun`/`DiscoveredDomain`.

## 2. Confirmed bugs

### Backend

1. **The scheduled discovery pipeline likely never actually crawls anything.** `discover_websites_task` (`tasks.py:139-152`) calls `crawl_domain_task.delay(...)` for each discovered domain, then *immediately* sets `run.status = SUCCESS` and persists it in the same function's `finally` block — all before any queued child task has executed (`.delay()` only enqueues). Every child task's first line checks `_run_is_cancelled(run_id)`, which treats **any non-`RUNNING` status — including the `SUCCESS` this same function just wrote — as cancelled**. On Windows with the default `CELERY_WORKER_POOL="solo"` (which processes tasks strictly one at a time), `discover_websites_task` is guaranteed to fully complete — writing `SUCCESS` — before the first `crawl_domain_task` even begins, so **every domain from a scheduled run silently self-aborts with `{"skipped": "run_not_running"}`**: no crawling, no scoring, no Prospects, from the pipeline the project's own docs call primary. This is very plausibly why crawler-sourced leads look sparse/absent in practice.

2. **Manually triggered crawls never reach a terminal status.** The admin "Trigger crawl" action and the dashboard's single-domain crawl trigger (`dashboard/api/views.py:359-367`, `admin_views.py:649-656`, `crawler/admin.py:120-136`) create a `CrawlRun` with `status=RUNNING` and enqueue `crawl_domain_task`, but nothing ever sets that run's terminal status afterward — only `discover_websites_task` does that, and only for the run it created itself. Every manually triggered domain crawl leaves its `CrawlRun` permanently `RUNNING`, indistinguishable from a hang.

3. **One failed page fetch marks an entire domain crawl as failed, even when almost everything succeeded.** `crawler.py`'s `error` variable is set once on any fetch exception (line 296) and **never cleared** on a later successful fetch, so it always reflects the *last* failure, not the overall outcome. `crawl_domain_task` then sets `crawl_status = "failed"` whenever `error` is truthy at all (`tasks.py:179`). A domain where 24/25 pages succeeded and only one transient 404/timeout occurred is recorded as fully failed — even though `analyze_domain_task` still runs on the successfully collected pages and may still create a Prospect. Operators see "failed" on domains that actually produced leads.

4. **Domains marked failed are never retried automatically, and a real retry mechanism exists in the schema but was never wired up.** `discover_websites_task` only re-queues `DiscoveredDomain` rows with `crawl_status="pending"` — once a domain flips to `"failed"` (including via the false positives in #3), it's permanently excluded unless a human manually resets it. `DiscoveredDomain.next_attempt_at` is defined and indexed on the model but is **never written anywhere** except being cleared to `None` by the manual "reset" actions — the backoff/retry scheduling this field clearly implies was planned but never implemented.

5. **Configured task retries never actually fire.** `discover_websites_task`, `crawl_domain_task`, and `analyze_domain_task` are decorated with `max_retries`/`default_retry_delay`, but none of their `except` blocks call `self.retry(exc=exc)` and none use `autoretry_for` — they just `raise`. Celery does not auto-retry on a bare exception without one of those mechanisms, so the retry configuration is dead code: any transient failure (e.g., a DB blip) permanently fails that task with zero retries.

6. **A domain can get stuck `crawl_status="crawling"` forever if the worker dies mid-crawl.** The status is saved *before* the (potentially minutes-long) `crawl_domain()` call. If the worker is killed (OOM, deploy, hard time limit) in between, the domain is left at `"crawling"` indefinitely — not picked up by the scheduled task (which only queries `"pending"`), and no periodic sweep exists anywhere to reset stale rows.

7. **Scheduled crawl runs can dedupe/overwrite Prospects across different owners.** `create_or_update_prospect` (`prospect_pipeline.py:54-62`) only scopes its dedup lookup by owner `if owner_id:` is truthy. The Celery Beat entry for `discover_websites_task` calls it with no arguments, so `initiated_by_id=None` for every scheduled run, propagating through the whole chain to `create_or_update_prospect(..., owner_id=None)`. For the primary automated pipeline, dedup then searches `Prospect.objects.all()` **unfiltered by owner** — if a new lead's hash/email/website happens to match an existing Prospect owned by a *different* user, that other user's record gets silently overwritten rather than a new Prospect being created.

8. **Rate-limit and crawl-depth config is computed and stored but never actually used.** `_get_crawler_config()` reads `CRAWLER_RATE_LIMIT_SECONDS` from env and snapshots it onto `CrawlRun.config`, but `crawler.py:250` always constructs the rate limiter from a hardcoded constant, ignoring the env var entirely. `DEFAULT_MAX_PAGES_PER_DOMAIN`/`DEFAULT_MAX_CRAWL_DEPTH` are similarly hardcoded and never sourced from the run's config despite the field's docstring implying they should be overridable per run.

9. **The discovery-time qualification fetch bypasses robots.txt and rate limiting entirely — unlike the BFS crawler.** `discovery_qualify.py` → `fetch_page_for_qualification` (plain httpx, no robots check, no delay) is called once per discovered search hit, synchronously in a loop over up to 20 hits × N enabled sources, with zero delay between requests. The later BFS crawl of the same domain *does* respect robots.txt/rate limits — this earlier, higher-volume fetch path doesn't, and can hit target hosts back-to-back with no politeness control.

10. **`EventProspect` has no DB-level uniqueness constraint**, only an application-level `update_or_create` keyed on `(event_name, organizer_domain)` (`event_processor.py:71-99`). Two concurrent `analyze_domain_task` runs for the same domain — nothing prevents this, since `DiscoveredDomain` has no crawl-in-progress lock beyond the non-atomic `crawl_status` field — can both create separate `EventProspect` rows for the same event before either transaction commits. `CrawlRunDomainResult` has explicit unique constraints for exactly this kind of race; `EventProspect` doesn't.

### Frontend

11. **The entire "ad-hoc discovery" workflow calls backend endpoints that don't exist.** `crawlerPreview` and `crawlerQueue` (`shared/api/crawler.ts:87-109`) POST to `/dashboard/api/crawler/preview/` and `/dashboard/api/crawler/queue/` — grepping the entire backend (URL config, views, any DRF router) for these paths returns zero matches anywhere. `CrawlerDiscoverPage.tsx` — the whole "Preview URLs → Add to queue → Queue & crawl now" flow — is fully wired up in the UI but every core action will 404 against the real backend. Opening `/crawler/discover` and clicking "Preview URLs" fails with a generic axios error banner instead of results.

12. **The "Running now" stat on the staff crawler dashboard undercounts.** `CrawlerHomePage.tsx:74-75` computes it by filtering the 10 most-recently-fetched runs (`listCrawlRuns({ page_size: 10 })`, no status filter) client-side, instead of issuing a dedicated `page_size:1, status:'running'` count query like every other stat on the same page does (and like the admin equivalent, `CrawlerAdminStatsCards.tsx`, correctly does). If there are more running runs than fit in the 10 most recent, the staff dashboard understates the true count — a real drift between the staff and admin overviews computing the "same" number two different ways.

13. **No error handling on any read query across the entire crawler feature, staff or admin.** Every `useQuery` in `CrawlerHomePage`, `CrawlerDomainsPage`, `CrawlerRunsPage`, `CrawlerRunDetailPage`, and all the `AdminCrawler*Table`/`CrawlerAdminStatsCards` components never checks `.isError`. `AlertBanner` is only ever driven by mutation failures. A failed GET after initial load (backend down, session expired) leaves stale/zero data on screen with no visible indication — indistinguishable from a legitimately empty result.

14. **`StatusBadge`'s `kind` prop is dead — declared, passed by every caller, never read.** `StatusBadge({ status, className })` (`StatusBadge.tsx:23-31`) destructures only two of the three declared props; `kind="crawl"`/`kind="run"` are passed everywhere under the belief that colors are scoped per-domain, but all statuses across all "kinds" actually share one flat color map. Not currently colliding, but misleads future contributors into thinking kind-specific theming exists.

15. **Run status color lookup is keyed off the human-readable label, not the status code, and is fragile to future label changes.** `RunStatusBadge.tsx:4` passes the `display` label (not the raw status) into `StatusBadge`, which lowercases it to look up colors. This only works today because current `CrawlRun` display labels ("Running"/"Success"/"Failed") happen to lowercase to the exact color-map keys — any future multi-word label (e.g. "In Progress") would silently lose its color with no test or type catching it.

## 3. Design concerns / tech debt

16. **Dead/orphaned admin component files confirmed still present.** `frontend/src/components/admin/crawler-admin-sections.tsx`, `crawler-admin-subnav.tsx`, `scraper-admin-sections.tsx`, `scraper-admin-subnav.tsx` all still exist and are still unreferenced anywhere in `frontend/src` (matches the original `CODEBASE_REANALYSIS.md` finding — unchanged since then).

17. **Centralized query-key helpers exist but are only partially adopted.** `crawlerKeys.domains(...)`/`.runDomains(...)` and `adminKeys.crawler.domains(...)`/`.runs(...)` are all defined but never called — the actual high-traffic pages use raw inline array literals instead, so the "centralized" registry doesn't centralize the two highest-traffic lists.

18. **No CrawlSource creation or deletion exists anywhere, staff or admin, frontend or backend.** The only write operation is a PATCH-only update (enabled/priority/name/discovery_query/source_type) — confirmed no POST/DELETE route exists on the backend either. Worth noting explicitly since it's easy to assume a "manage sources" form exists somewhere and go looking for its validation.

19. **Duplicated stats-card implementations have already drifted in more than one way.** Staff's `CrawlerHomePage` uses 6 independent queries with individually tuned poll intervals (5-25s); admin's `CrawlerAdminStatsCards` uses 3 queries with **no polling at all**. Same underlying numbers, computed by separate hand-rolled queries with no shared hook — one auto-refreshes, the other only updates on manual navigation. Compounds with bug #12 above.

20. **Wasteful "count via page_size=1" pattern repeated ~10 times across the feature** instead of a dedicated stats/counts endpoint — each is a full serialized backend list-view call just to read `.total`.

21. **A working SSE stream exists but the crawler pages don't use it.** The backend's per-run and general run-status SSE streams (and the frontend hook that consumes them, `useRunsStream.ts`) are fully wired — but used only by the unrelated `StaffHomePage`. `CrawlerRunsPage`/`CrawlerRunDetailPage` instead do plain 5s polling, missing an opportunity to reuse the "live" infrastructure exactly where a user would watch a single run's progress.

22. **Domain-result state values are mostly uncolored.** Backend `CrawlRunDomainResult.STATE_CHOICES` (`queued/crawled/analyzed/scored/failed`) are all selectable in the results filter, but `StatusBadge`'s color map only has an entry for `failed` — the other four states all render as the same flat gray badge, defeating the purpose of a status-colored table.

23. **Accessibility gaps on filter controls**, inconsistent with the properly-labeled `CrawlerDiscoverPage` search fields: every bare `<Select>` filter across domains/runs/run-detail/admin-domains/admin-runs pages, plus the domain search input, has no accessible name beyond visible option text.

24. **Duplicate-key risk in the (currently broken, per #11) discovery preview table.** `normalizeDiscoveryEntry`'s row ID falls back to `` `${domain}-${i}` `` only when `landing` (the source URL) is empty — if a search response contains duplicate URLs, two rows get the same React key, silently merging their checkbox selection state.

25. **Test coverage gaps.** Backend: zero tests for the BFS crawl (`crawler.py`), any of the Celery tasks (`discover_websites_task`/`crawl_domain_task`/`analyze_domain_task`/`score_and_create_prospect_task`), `models.py`, `prospect_pipeline.py`, `scoring.py`, `analyzer.py`, `extractor.py`, `domain_pipeline.py`, `event_processor.py`, discovery's dedup logic, admin actions, or any crawler dashboard API endpoint — everything tested is shared qualification/filter service code also used by AI search. This is plausibly why bug #1 (the run-status race) has never been caught: Celery's eager test mode runs `.delay()` synchronously inline, which would mask the race entirely. Frontend: `discoverUtils.test.ts` only covers one of four exported functions in that file.

## 4. Verified working / not bugs

- No model/migration drift found (`CrawlSource`/`CrawlRun`/`DiscoveredDomain`/`CrawlRunDomainResult` all match their migrations exactly; the two divergent `0003_*` migrations are a reconciled branch merge, not drift).
- The `score > CRAWLER_MIN_SCORE_THRESHOLD` gate is correctly wired end-to-end with no drift between docstring and behavior.
- All crawler and admin-crawler frontend pages are correctly routed and reachable — no orphaned pages among the ones actually meant to be live.
- Polling correctly stops at terminal states and cleans up on unmount everywhere it's used (TanStack Query handles this automatically).
- No `any`/`as any`/`@ts-ignore`/`@ts-expect-error` anywhere in the crawler frontend or its shared API layer.
- Domain search is properly debounced (300ms) — no request-per-keystroke issue.

## 5. Cross-cutting observations

- **Finding #1 is the single most consequential bug found across all three feature audits so far** (AI search, scraper, crawler): if confirmed in the live deployment, the scheduled crawler pipeline — described as the *primary* lead source in the project's own docs — has likely never produced a single Prospect via its normal schedule, only via manual single-domain triggers (which then hit bug #2 and never show a completed status). Worth verifying against production Celery worker pool configuration before assuming it's live-broken, but the logic is unconditional given the default Windows `solo` pool.
- As in the other two features, backend task-level error handling is reasonable in isolation (bugs are about status transitions and retries, not crashes), while the frontend has no error state anywhere for failed list/detail fetches — every failure looks like "nothing here."
- The discovery-qualify fetch path (#9) is a second, unthrottled network path alongside the properly-throttled BFS crawler — the same politeness gap noted for the AI search feature's extraction path in `AI_SEARCH_ANALYSIS.md`, suggesting rate-limiting discipline wasn't applied consistently across all outbound-fetch call sites in the codebase.
