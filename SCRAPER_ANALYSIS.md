# Scraper Feature — Full-Stack Analysis
*Generated 2026-07-19*

## 1. How it works, end to end

**Backend** (`backend/scraper/`): a `ScrapeTarget` (a configured URL + CSS-selector `config`) runs on a schedule (`run_every_minutes`, default 60). Celery Beat's `enqueue_enabled_targets` task (interval `SCRAPE_ALL_INTERVAL_SECONDS`, default 300s) finds due targets and enqueues `scrape_target`, which creates a `ScrapeRun`, fetches the page (`services/fetch.py` — plain HTTP or Playwright-in-subprocess for JS-rendered sites), extracts items via CSS selectors (`services/extract.py`), and upserts them into `leads.Prospect` (`services/upsert.py`). Stage-2 enrichment (`services/enrichment.py`) later backfills contact info from each item's detail page. Targets can be created manually, via bulk `sync_targets.py` (JSON/YAML config file), or via an auto-detection wizard (`services/auto_discover.py`) that generates a platform-specific config (Eventbrite, Meetup, Facebook, Eventful, Brown Paper Tickets, Ticketmaster, or a generic fallback) from a single URL.

**Frontend** (`frontend/src/features/scraper/` + `features/admin/scraper/`): `TargetsPage`/`TargetFormPage` manage targets, `TargetWizardPanel` drives the "Analyze URL → auto-detect config" onboarding flow, `RunsPage`/`RunDetailPage` show scrape run history and live status via polling. Admin has parallel, less-featured pages over the same data. All scraper HTTP endpoints live in `dashboard/api/` and `core/views.py` — `backend/scraper/views.py` is an unused stub.

## 2. Confirmed bugs

### Backend

1. **Auto-detected platform configs silently discard scraped titles and dates on every run.** Every platform config generated by `services/auto_discover.py` (Eventbrite, Meetup, Facebook, Eventful, Brown Paper Tickets, Ticketmaster, and the generic fallback) uses field keys `full_name` for the title and `event_date` for the date. But `upsert.py`'s `_map_item_to_prospect_fields()` (lines 33-53) only reads `["event_name", "event_text", "date_text", "event_description", "description"]` into `Prospect.event_name` — there is no mapping for `full_name` or `event_date` at all, and no `full_name` field exists on `Prospect`. **Every target created through the wizard — the primary onboarding path — extracts the item title/date correctly and then drops both silently during upsert**, with no error surfaced anywhere. This alone plausibly explains why Stage-1 scraping "works" (runs complete, Prospects get created) while looking incomplete/low-quality in practice.

2. **Relative URLs saved unresolved, breaking Stage-2 enrichment on non-Eventbrite platforms.** `extract.py:101,122-125` returns `@attr` values (e.g. `href`) raw, never resolved with `urljoin` against the page URL — unlike `runner.py:97`, which does resolve pagination links. Any platform emitting relative hrefs (Meetup, Facebook, and the generic fallback config all do) gets a relative path saved as `Prospect.source_url`. Stage-2 enrichment (`enrichment.py:58`) then calls `requests.get()` on that relative string, raising `MissingSchema`, caught by a broad `except Exception` and reported only as `"Failed to fetch detail page"` — masking the real cause. Strong candidate for why only Eventbrite (absolute URLs) was ever validated end-to-end.

3. **Uncaught exception when a stale/deleted target ID reaches `scrape_target`.** `tasks.py:166-176`: `ScrapeTarget.objects.get(id=target_id)` and `ScrapeRun.objects.create(...)` both run *before* the `try:` block. If the target was deleted after being enqueued (or a stale ID hits `/ops/trigger-scrape`), `ScrapeTarget.DoesNotExist` propagates uncaught — no `ScrapeRun` row is ever created, so the failure is invisible anywhere except Celery worker logs.

4. **Failed targets are retried forever with no backoff or auto-disable.** `target.last_run_at` (`tasks.py:211-212`) is only updated on the success path. On any failure, `last_run_at` stays stale, so `_target_is_due()` keeps returning `True` on every beat tick (`SCRAPE_ALL_INTERVAL_SECONDS`, default 300s) — forever. Each retry also fires `create_notification_for_all_users` and `log_activity`, so a permanently broken target spams notifications/activity logs indefinitely.

5. **Concurrency guard has a check-then-act race and is bypassed entirely on manual triggers.** `_target_has_run_in_progress` (`tasks.py:109-119`) only finds a `RUNNING` `ScrapeRun` — but that row is created *inside* `scrape_target` itself, not at enqueue time, leaving a race window where the same target gets double-enqueued (next beat tick, or a parameterless `/ops/trigger-scrape` call). Worse, **every manual trigger path bypasses the guard entirely**: `dashboard/api/views.py:163-177` (trigger), `admin_views.py:468-483`, `views.py:208-219`/`admin_views.py:504-524` (retry), and `admin.py`'s admin actions all call `scrape_target.delay(...)` directly with no guard check. A portal user can click "Run Scrape" repeatedly and launch many concurrent Playwright subprocesses for the same target — real resource exhaustion on the worker host. Separately, the guard's 600s window (`SCRAPE_CONCURRENCY_GUARD_SECONDS`) can be shorter than a legitimately slow multi-page Playwright scrape, letting the next beat tick re-enqueue a duplicate of a still-genuinely-running scrape.

6. **Playwright subprocess can be force-killed before its own graceful partial-content path fires.** `fetch.py:168`: `wall_clock_timeout = timeout_ms/1000 + 15`. But `page.goto(timeout=timeout_ms)` and `page.wait_for_selector(timeout=timeout_ms)` (lines 90, 109) each independently budget the full `timeout_ms` — worst case ~2×`timeout_ms` — while the outer `subprocess.run(timeout=wall_clock_timeout)` only budgets `timeout_ms + 15s`. For the shipped Meetup config (`timeout_seconds: 90`), the subprocess can be killed by `TimeoutExpired` before Playwright's own "return partial HTML" fallback gets a chance, turning a soft partial-content warning into a hard failure.

7. **Timed-out Playwright subprocesses leave zombie browser processes on Windows.** `fetch.py:182-192`: on `TimeoutExpired`, only the immediate Python subprocess is killed — the Node driver and `chrome.exe` it spawned are not part of that process handle, and there's no Job Object / `taskkill /T` cleanup. Windows gives no automatic child-tree cleanup here, so repeated timeouts (made more likely by bug #6) accumulate orphaned Chromium processes on the worker host indefinitely.

### Security

8. **SSRF: no host validation on `start_url` anywhere in the pipeline.** `ScrapeTarget.start_url` is a plain `URLField` (format-only validation); `ScrapeTargetSerializer` adds nothing extra; `targets_list` POST is reachable by any user in the `scraper` group (not just staff/admin) via `IsDashboardPortalUser`. Nothing in `fetch.py`/`fetch_html_playwright`/`runner.py` blocks `localhost`, RFC1918 ranges, or cloud metadata IPs (`169.254.169.254`). A non-admin portal user can create a target pointing at an internal service and read the response back through their own Prospect records. `/ops/auto-create-target` has the identical gap, gated only by an `OPS_TOKEN` header compared with `==` rather than `hmac.compare_digest` (minor timing-attack hardening gap, `core/views.py:14-18`).

### Frontend

9. **The URL-assistant field doesn't sync to the loaded target on the edit page.** `TargetWizardPanel.tsx:41`: `useState(initialUrl)` never re-syncs when `initialUrl` changes after the panel has already mounted. On `TargetFormPage.tsx`, the panel mounts with `startUrl=''` (detail hasn't loaded yet); once `detailQ.data` arrives, the wizard's own `url` state stays stuck empty — the "Re-analyze" flow is broken on every edit-target page load until the user manually retypes the URL.

10. **In-progress form edits get silently discarded by an unrelated action.** `TargetFormPage.tsx:51-61`'s hydration `useEffect` re-runs on *any* refetch of the target query, not just initial load. Editing the Name field, then clicking "Scrape now" (which invalidates the same query key on success) triggers a background refetch that resets all local form fields back to server values — the in-progress, unsaved edit vanishes with no warning.

11. **Wizard "Create" validates less strictly than the manual form for the same operation.** `TargetWizardPanel.tsx`'s `createM` only checks for valid JSON + non-empty url/name — never for `item_selector`/`fields` presence, unlike the manual path's `buildTargetPayload`. The backend's `wizard_create_target` does no schema validation either. A user who clears/edits the detected config in "Smart setup" mode can create a target that only fails later, asynchronously, on the Runs page — disconnected from the wizard action that caused it.

12. **Default manual-JSON template uses a field name the backend silently drops.** `utils.ts`'s `DEFAULT_TARGET_CONFIG_JSON` uses `title`, which (per backend finding #1) isn't in `_map_item_to_prospect_fields()`'s read list either — a target created straight from this placeholder produces Prospects with a blank `event_name`.

13. **Target/run lists silently cap at 200 with no indication of truncation.** `TargetsPage.tsx` and `RunsPage.tsx`'s target filter both call `listTargets({ page_size: 200 })` and do all filtering/pagination client-side over that capped set. Past 200 targets, search misses matches beyond the first page and some targets become unselectable in filters — with zero UI indication that results are incomplete.

14. **`run_every_minutes: 0` silently becomes 60, not 1.** `buildTargetPayload`: `Math.max(1, Math.floor(fields.runEvery) || 60)`. Entering `0` evaluates `Math.floor(0) || 60` — the falsy `0` triggers the `60` fallback instead of the `Math.max(1, ...)` floor the code visually suggests, silently rewriting the user's input to the default interval.

15. **No error state anywhere in the scraper UI — every failed fetch renders as an empty list, not an error.** None of `RunDetailPage`, `RunsPage`, `TargetsPage`, `AdminScraperRunsTable`, `AdminScraperTargetsTable`, or `ScraperAdminStatsCards` check `.isError` on their queries. A failed fetch renders as "No scrape runs match your filters," "No targets match your filters," a blank run detail page, or admin stat cards silently showing "0" — all indistinguishable from legitimately empty/zero state.

## 3. Design concerns / tech debt

16. **Dedup falls back to a fragile whole-payload hash almost every time.** `upsert.py:74-82` matches by email → phone → raw-payload SHA-256, with no matching on `source_url`. Since Stage-1 listings rarely populate email/phone (see below), dedup nearly always uses the payload hash — any drift in listing text between scrapes (relative dates like "in 3 days", live spot counters) changes the hash and silently creates a duplicate `Prospect` for the same real event instead of updating it. `source_ref` exists in the mapping but no shipped platform config ever populates it.

17. **Cross-tenant dedup/overwrite risk for system-provisioned targets.** Matching is only owner-scoped `if owner_id:` — but `ScrapeTarget.owner` is nullable, and both `sync_targets.py` and `/ops/auto-create-target` create targets with `owner=None`, so their upserts match against `Prospect.objects.all()` unfiltered by owner. In a genuinely multi-tenant deployment, one user's scrape could update another user's `Prospect`.

18. **Null-owner targets are invisible to everyone except superusers in the dashboard API**, while still being fully manageable via Django admin — the two documented provisioning paths (`sync_targets`, `/ops/auto-create-target`) both produce targets that regular portal users can't see or manage through the UI at all.

19. **Stage-2 enrichment skip condition is too broad.** `enrich_prospect()` skips entirely if the prospect already has *either* `email` **or** `company` — so a prospect with only `company` populated from Stage 1 never gets enriched for `website`, `location`, `event_datetime`, or `event_description` either, even though those are typically still empty.

20. **No server-side config schema validation.** `ScrapeTargetSerializer` is a plain `ModelSerializer` around a JSON field; `item_selector`/`fields` requirements are enforced only client-side in `buildTargetPayload`. Anyone calling the API directly can persist an unusable config that only fails asynchronously at scrape time — matches Django admin's stricter `ScrapeTargetAdminForm.clean_config`, which the API doesn't share.

21. **Confirmed still-dead code from the prior full-codebase audit:**
    - `frontend/src/shared/api/index.ts` still exports `triggerScrape`/`getRunStatus`/`retryRun` hitting legacy `/dashboard/api/trigger-scrape/`-style URLs with zero remaining callers (superseded by `scraper.ts`'s `v1/...` equivalents).
    - `frontend/src/components/admin/scraper-admin-sections.tsx` / `scraper-admin-subnav.tsx` are still present, still unreferenced anywhere, and turned out to be thin re-export shims pointing at the real `features/admin/scraper/*` components — pure dead weight, not a second implementation.
    - `backend/scraper/views.py` is an empty stub; there's no `scraper/urls.py` and nothing imports it. All scraper endpoints live in `dashboard/api/` and `core/views.py`.
    - `enrichment.py:19` imports `extract_items` but never uses it.

22. **Staff vs admin scraper UI capability drift.** `AdminScraperTargetsTable` has no search/enabled-only filter despite the backend supporting both (staff's `TargetsPage` has full filtering). `AdminScraperRunsTable` has a status filter but no target filter, despite the backend supporting `target_id` (staff's `RunsPage` has both). Admin types (`AdminScraperTarget`/`AdminScrapeRun`) carry only raw `owner_id`, forcing admins to cross-reference the Users page to identify an owner, unlike the AI-search admin surface elsewhere in the app which includes `owner_username`.

23. **Error miscategorization can silently swallow real failures.** `tasks.py:271-276`'s `is_config_error` uses bare substring checks (`"selector" in error_lower or "css" in error_lower`) with no context — any unrelated exception whose message happens to contain those words gets classified as a config error and silently swallowed rather than surfaced.

24. **Admin bulk-trigger vs. single-trigger inconsistency.** The bulk admin action `trigger_scrape_selected` checks `target.enabled` before enqueueing; the per-row "Run Scrape" button's handler does not — a disabled target can still be manually triggered from its own admin detail page.

25. **Regex-based contact extraction has no scoping.** `enrichment.py:246-267`'s email/phone regexes run over the entire page text with no scoping to a contact section — share widgets, ads, footer boilerplate can all be captured as if they were the organizer's contact info. Data-quality risk, not a crash.

26. **No floor on scrape frequency.** `run_every_minutes` allows `0`, which makes a target due again essentially immediately after each run — no server-side minimum to prevent hammering a third-party site, beyond whatever the beat interval and (bypassable, per #5) concurrency guard happen to provide.

27. **Doc/config mismatch.** `TWO_STAGE_SCRAPING.md` claims Stage 1 "runs every 2 hours," but the actual default `run_every_minutes` is 60 and the beat check interval defaults to 300s — neither matches the documented 2-hour cadence.

28. **Prior-audit findings reconfirmed as still accurate:** PyYAML is guarded-but-absent from `requirements.txt` (YAML target sync fails cleanly with `CommandError`, not silently); only Eventbrite scraping was ever validated end-to-end (consistent with backend bug #2 above plausibly breaking other platforms); Stage-2 contact enrichment mostly doesn't work per the project's own `TWO_STAGE_SCRAPING.md`; the `leads/migrations` 0002→0004 gap is confirmed leads-app-only and not scraper-relevant (scraper's own migrations have no drift).

29. **Minor accessibility gaps**, isolated to filter/search controls (not the wizard's main fields, which are properly labeled): `TargetsPage`'s search input has only a placeholder, no `<label>`; both filter `Select`s on `RunsPage` and the status `Select` on `AdminScraperRunsTable` have no label/`aria-label`. Separately, `TargetWizardPanel` is a progressive-disclosure form rather than a true stepped wizard, and newly-revealed fields don't receive focus (only the status banner is announced to screen readers).

## 4. Cross-cutting observations

- **Finding #1 (backend) is the single highest-impact bug in this feature**: it silently breaks the primary onboarding path (the auto-detection wizard) for every supported platform, with no error anywhere in the pipeline — runs "succeed," Prospects get created, but with blank titles/dates. This was invisible to both the backend and frontend audits individually and only became clear by cross-referencing the wizard's generated config field names (frontend finding) against the upsert mapping (backend finding).
- The concurrency-guard bypass on all manual triggers (#5) combines badly with the zombie-process risk (#7) and the lack of an SSRF guard (#8): a user can repeatedly trigger scrapes against an internal address, each spawning an unkillable-on-timeout Chromium process.
- As with the AI search feature, error handling *within* a run is reasonable, but the UI has no error state anywhere for failed *fetches* of run/target lists themselves — every failure looks identical to "there's nothing here."
- No test coverage gaps were separately catalogued here since the backend audit didn't focus on `scraper/tests.py` coverage explicitly, but no test references appear for any of the concurrency, SSRF, or field-mapping bugs above.
